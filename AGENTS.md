# AGENTS.md

## Назначение

Этот файл фиксирует эталонные правила разработки для `RUF-API-Platform`.
Все новые доработки, рефакторинг и исправления выполняются в соответствии с этими правилами.

## Текущий стек

- Frontend: `React 19`, `TypeScript 5`, `Vite 7`
- Desktop shell / native commands: `Tauri 2`
- Backend-команды desktop-приложения: `Rust 2021`
- Линтинг: `ESLint 9`
- Сборка UI: `tsc -b && vite build`

## Базовые правила

- Все текстовые файлы проекта создаются и редактируются в кодировке `UTF-8`.
- Перед изменением нужно понять локальный контекст конкретного модуля, а не абстрактно "улучшать проект".
- При доработке фич не сканируем весь репозиторий без необходимости.
- Сначала ищем точечно: по имени модуля, функции, типу, команде Tauri, UI-компоненту, ключу storage, route, tab extension.
- Для поиска используем быстрый адресный поиск: `rg`, `rg --files`, поиск по конкретной папке (`src/modules/...`, `src/shared/...`, `src-tauri/src/commands/...`).
- Если задача локальная, не трогаем соседние модули "заодно".
- Любое изменение должно быть минимально достаточным: без лишних переименований, перемещений и шумовых правок.

## Правила для версии приложения

- Если задача включает поднятие версии приложения, обновляем только app-level version-поля, а не версии зависимостей.
- Версия приложения должна быть синхронизирована минимум в:
  - `package.json`
  - `package-lock.json`
  - `src-tauri/Cargo.toml`
  - `src-tauri/tauri.conf.json`
- Если меняется только версия приложения, не трогаем semver-записи библиотек, crates и tooling-зависимостей без отдельной задачи.
- После изменения версии в `package.json` синхронизируем `package-lock.json`, чтобы его корневая версия не оставалась старой.

## Принцип модульности

- Основная единица организации на frontend: изолированный модуль в `src/modules/<module-name>`.
- Общие cross-module сущности размещаются в `src/shared`.
- Базовые контракты, контекст приложения и bootstrap-логика размещаются в `src/core` и `src/app`, если это действительно уровень приложения, а не отдельной фичи.
- Каждый модуль должен иметь ясную публичную точку входа через `index.ts`, экспортирующую только нужный внешний API.
- Нельзя импортировать внутренности модуля из случайных вложенных файлов, если для этого уже есть публичный экспорт.
- Если логика относится только к одному модулю, она остается внутри модуля и не выносится в `shared` преждевременно.
- Вынос в `shared` допускается только когда код реально переиспользуется или является очевидной общей инфраструктурой.

## Переиспользование и композиция

- Перед добавлением новой функции нужно проверить, нет ли уже близкой реализации в текущем модуле или в `src/shared/utils`.
- Предпочтительно расширять существующий helper, сервис, утилиту или тип, если это не ломает читаемость.
- Запрещено дублировать:
  - преобразование данных;
  - работу с `localStorage` / persistent storage;
  - HTTP / platform / Tauri invoke-обертки;
  - парсинг JSON / YAML / schema;
  - tree traversal и collection traversal;
  - одинаковую UI-логику в нескольких компонентах.
- Если повторение появилось второй раз, нужно остановиться и выделить общее решение.
- Переиспользование не должно приводить к "god utility": лучше маленькая специализированная функция рядом с доменом, чем огромный общий файл обо всем.

## Правила для TypeScript / React

- Соблюдаем `strict`-подход, заложенный в `tsconfig`.
- Новые типы должны быть точными и доменными; `any` допустим только на реальных динамических интеграционных границах.
- Не добавляем неявные преобразования там, где можно выразить тип через `type`, `interface`, union или utility type.
- UI-компоненты должны оставаться тонкими: сложную трансформацию данных, поиск, нормализацию, storage-логику и orchestration выносим в utils / services / hooks.
- Компоненты не должны содержать несвязанные обязанности одновременно: рендеринг, бизнес-логику, persistence и сетевое взаимодействие лучше разделять.
- Повторяемые табы, расширения и plugin-like механики продолжаем оформлять в существующих registry / extensions паттернах проекта.
- Баррель-экспорты (`index.ts`) используем для публичного API модуля, но не превращаем их в свалку всех внутренних файлов.
- Имена должны отражать назначение:
  - `components/` для UI;
  - `utils/` для чистых функций;
  - `services/` для orchestration / application logic;
  - `types.ts` или `shared/types` для контрактов;
  - `extensions/` для расширяемых UI-регистров.

## Правила для Tauri / Rust

- Команды Tauri размещаются в `src-tauri/src/commands`.
- Новая команда должна добавляться в профильный файл команды, а не в случайное место:
  - HTTP в `http.rs`
  - DB в `db.rs`
  - storage в `storage.rs`
  - terminal в `terminal.rs`
  - system в `system.rs`
  - cert в `cert.rs`
  - mocker в `mocker.rs`
- Если появляется новый домен, допускается новый файл команды и регистрация через `mod.rs` и `main.rs`.
- В Rust избегаем дублирования DTO, ошибок и ответов; общие структуры выносим рядом с доменом.
- Границы между frontend и Tauri-командами должны быть стабильными: сначала проектируем контракт запроса/ответа, потом реализацию.
- Нельзя добавлять новую native-логику в UI, если она должна жить на стороне Tauri.

## Работа с изменениями фич

- При доработке существующей фичи сначала ищем:
  - точку входа модуля;
  - основной UI-компонент;
  - связанные utils/services;
  - типы данных;
  - storage / invoke / runner / extension integration.
- Не читаем весь проект подряд.
- Не делаем глобальный рефакторинг, если задача локальная.
- Если затронута существующая архитектурная граница, сначала сохраняем текущий паттерн проекта и только потом расширяем его.
- Если видно несколько похожих реализаций, выбираем ту, которая уже является фактическим центром поведения, и достраиваем ее вместо создания еще одной ветки логики.

## Стиль реализации

- Предпочтение отдается небольшим функциям с одной ответственностью.
- Сложные ветвления упрощаем ранними возвратами и декомпозицией.
- Побочные эффекты должны быть локализованы и заметны по имени функции.
- Комментарии добавляются только там, где без них трудно понять мотив или ограничение.
- Не добавляем шумовые абстракции "на будущее", если текущий кейс этого не требует.
- Не смешиваем массовые форматирующие правки с логическими изменениями без необходимости.

## Проверка перед завершением

- Для изменений UI / TS по возможности проверяем:
  - `npm run lint`
  - `npm run typecheck`
- Для изменений, влияющих на сборку UI:
  - `npm run tauri:ui:build`
- Для изменений в Tauri / Rust:
  - по необходимости проверяем соответствующую сборку или compile path без лишнего полного прогона, если задача локальная.
- Если полная проверка слишком дорогая для локальной правки, выполняем минимально релевантную проверку и явно фиксируем это в результате.

## Чего не делаем

- Не сканируем весь код проекта при каждой задаче.
- Не копируем куски логики в новый файл вместо переиспользования.
- Не выносим код в `shared`, если он нужен только одному модулю.
- Не ломаем публичные контракты модулей без явной причины.
- Не смешиваем в одном изменении архитектурный рефакторинг и фича-фикс, если это можно разделить.
- Не добавляем новые зависимости без реальной необходимости и без проверки, что текущий стек уже не решает задачу.

## Короткий рабочий алгоритм

1. Найти точку изменения адресным поиском.
2. Прочитать только релевантные файлы текущего модуля и его ближайших зависимостей.
3. Найти существующие типы, утилиты и публичные точки расширения.
4. Внести минимальное модульное изменение с переиспользованием текущих механизмов.
5. Проверить только релевантные сценарии и команды.
6. Зафиксировать ограничения или технический долг, если он обнаружен, но не входит в задачу.
